## Context

- In this model the diary mode is only a start value; the location choice places activities without regard to it, and the discrete mode choice is what makes mode and distance consistent (ADR-0145 decision 1). It never reaches two groups of trips, so their diary mode survives the whole run: a 24 km walk of person 415371 started issue #678.
- The mechanism (verified in the code, 2026-11-25): the production tour finder splits at `home` and `outside`, `OutsideFilter` rejects a tour that starts or ends at `outside`, and `TourLength` rejects tours of more than 6 trips. A rejected tour keeps its initial modes. Every trip of a home-based tour that touches `outside` is therefore frozen, also the trips between two inside activities, and so is every tour over the length limit. `plan_check.leg_tour_frozen` mirrored only the first rule (it stays the rule where no reach settings are passed).
- eqasim already ships the finer rule (`ActivityTourFinderWithExcludedActivities`, bound in `BraunschweigModeChoiceModule` as `IsolatedOutsideTrips`, never selected). ADR-0141 decision 6 held that selecting it needs a separate decision.
- The measured size of both groups (trips, tours, long walks) is in the run manifest [`i678-mode-choice-reach-probe-prod100-2026-11-25`](../runs/i678-mode-choice-reach-probe-prod100-2026-11-25.yml): model output of the prepared population of `prod100_20261031`, the state before the simulation, not a validation. No number is repeated here.

## Decision

1. **Part A, reach.** Before iteration 0 the initial mode choice runs with the finer rule (`braunschweig.initial_mode_choice.isolate_outside_trips` true): only trips that start or end at `outside` stay fixed, tours up to 11 trips are chosen, as in the loop (`braunschweig.initial_mode_choice.max_tour_length`). `prepare` edits the final config with `braunschweig.matsim.simulation.mode_choice_reach` and writes a second config file for the initial choice; the loop config keeps the loop settings.
2. **Part B, repair.** `frozen_pt_walk_lift` keeps its name and report file. With `braunschweig.frozen_pt_walk_lift.all_modes` (true) it covers every resident trip the LOOP does not reach, whatever the reason: a pt-intended all-walk trip over the pt bound (today's rule), a walk trip over `braunschweig.plan_check.walk_max_distance_m`, a bicycle trip over `braunschweig.plan_check.bicycle_max_distance_m`. The replacement is one `car_passenger` leg (as ADR-0156, ADR-0187, ADR-0189). When a bicycle trip is lifted, every bicycle trip of its home-based tour goes with it (`lifted_with_tour`), because the bicycle would otherwise be left behind. Car trips are never lifted. The bound `braunschweig.frozen_pt_walk_lift.max_share_other_modes` (0.002) judges the lifted walk and bicycle trips over all resident trips.
3. **One definition of reach** (`plan_check.leg_reach`; `prepare` passes the loop settings, so the plan check and the repair use it): a trip is `fixed_border`, `fixed_vehicle`, `fixed_length` or reached. The repair and the plan check call it with the settings of the loop; the Java rule and the Python mirror are tested on the same named cases.
4. **Vehicle rule for border tours (Java, `BorderTourVehicleConstraint`, bound as `BorderTourVehicleContinuity`, eqasim-java-bs branch `feat/i678-border-tour-vehicle-rule`, not merged).** In a border tour (a home-based tour with a trip that touches `outside`) a vehicle leg (`car`, `bicycle`) keeps its mode and no other trip takes a vehicle mode; walk, pt and `car_passenger` are free. Outside border tours the stock `VehicleTourConstraint` decides unchanged. Vehicle legs of a border tour whose vehicle the person does not have (car without car availability or licence, bicycle without bicycle availability) are treated as free legs, counted and logged with a rate: otherwise no chain is feasible and the mode choice would throw (`fallbackBehaviour` is `EXCEPTION`).
5. **The loop starts with the coarse rule** (`braunschweig.mode_choice.isolate_outside_trips` false) and a length limit of 11 (`braunschweig.mode_choice.max_tour_length`; owner decision 2026-11-25). The initial choice uses the same limit of 11 (owner decision 2026-11-25 after the timing measurement, see Tour lengths).
6. **Plan check.** `summarise` classifies with the reach definition and the loop settings. New counters per block: `n_trips_fixed_border`, `n_trips_fixed_vehicle`, `n_trips_fixed_length`, `n_unreached_unfit`, and, for reached trips, `n_walk_trips_over_reached`, `n_bicycle_trips_over_reached` (report only). The invariant `n_unreached_unfit` = 0 after the lift raises regardless of `fail_on_threshold` when the lift covers all modes (a programming error, not a data threshold); with the lift off it is an ERROR line. The plan check takes "did the lift cover all modes" from the lift report, not from the config key.
7. **Switches and today's behaviour.** With the four mode choice values at today's (`false`, 6 for both) and `all_modes` false, the population and the MATSim config are byte-identical to today; only `plan_check.json` differs (decision 8).
8. **`plan_check.json` of legacy runs changes.** The classification knows the length filter in both switch states, so over-long tours now count as not reached also when the switches are off. This is the truth, accepted by decision: old run manifests keep their numbers and are not rewritten. Readers of `plan_check.json` are not rewritten by this record.
9. **Jar check.** With the switch on, `mode_choice_reach.require_border_vehicle_constraint` fails in `prepare` when the jar lacks the constraint class, so the message names the missing feature instead of an unknown component name.

## Rationale

**The three approaches.** A, reach (structural): the non-vehicle trips of border tours and the over-long tours get a real mode choice and react to prices and travel times; costs a Java change and a new comparison run. B, repair (symptomatic): remove the absurd walks, the trips stay inert; Python only. C, source: couple the location choice to the diary distance or mode; changes every distance in the model and touches work and school places (rejected for primary locations in ADR-0145). A and B together: A keeps the unreachable set small, B guarantees that nothing absurd is left in it, and because the loop never changes these trips the result holds for the whole run.

**The vehicle rule and what it gives up.** About six in ten of the freed trips are car or bicycle legs (probe output in the manifest). In a tour that leaves the area by car they have to stay car anyway. The rule gives up only park-and-ride-like tours that could drop the car altogether. A full vehicle state across fixed trips (track the vehicle, allow a consistent switch) is possible later with the `previousModes` argument; it is not needed to remove the defect. The stock `VehicleTourConstraint` would leave a car in front of a fixed trip, which is why it is not used inside border tours.

**Why the loop starts with the coarse rule.** A trip of a border tour that the mode choice reaches can still keep an unfitting mode when the person has no other option (no pt connection, no passenger availability). The repair cannot hold such a trip inside the loop, because the loop would choose again and drop a `car_passenger` leg the person may not use. With the coarse rule in the loop the order is: one real choice before iteration 0, then the repair for what is still unfitting, then nothing changes these trips, so the invariant holds for the whole run. Under the finer rule a lifted bicycle trip that was fixed as a vehicle leg becomes `car_passenger`, a non-restricted mode, so the loop can choose it again; this is one more reason the switch starts off. The replay counts the trips that would be left without a fitting option under the finer rule, and with that number the owner decides whether the loop switch goes on.

**Tour lengths.** The mode choice enumerates (available modes) to the power of (trips) chains per tour, so the work grows steeply with the limit; the enumeration counts per tour length are in the output of the cost probe in the manifest. The timing of the initial choice on the long tours is measured in the run manifest [`i678-long-tour-timing-prod100-2026-11-25`](../runs/i678-long-tour-timing-prod100-2026-11-25.yml). On that evidence the owner decided on 2026-11-25: limit 11 for the initial choice and for the loop. Tours longer than 11 trips stay unreached on purpose: they are counted and their unfitting trips are repaired by the lift (`frozen_pt_walk_lift`, all modes) and enforced by the plan check invariant.

**The bound `max_share_other_modes` (0.002).** ASSUMPTION, not committed evidence: a tripwire of about three times a share of lifted walk and bicycle trips that the design estimated from scratch probes before the reach was widened; the committed probe manifest holds the resident trip count but not that share. It is not a reference value. The replay of the next step measures the real share; if it exceeds the bound the builder stops and reports, and a bound is never tuned to make a run pass.

**What was left open and is closed here.** ADR-0141 decision 6: `IsolatedOutsideTrips` does not need the planned `PortalTripConstraint`; it needs a vehicle rule for the border tours, which decision 4 is. ADR-0145: its premise that the mode choice reaches every tour that is not frozen did not hold for border tours and over-long tours; the set of tours that rely on the synthesis' modes (its `outside_tour_modes` judgment) is unchanged, and the modes of trips that touch `outside` stay as decided there (ADR-0145, ADR-0159, ADR-0187). ADR-0189: its repair covered pt-as-walk in frozen tours only; decision 2 widens it to all modes and all reasons, with its definition of a long walk and its report file.

## Rejected options

- **C, source (couple the location choice to the diary):** see Rationale.
- **B alone:** the trips would stay inert and never react to prices or travel times.
- **The stock `VehicleTourConstraint` inside border tours:** leaves a vehicle at a place where it was never left, or throws.
- **A full vehicle-state rule across fixed trips:** larger, not needed for the defect (later option).
- **The finer rule in the loop by default:** see Rationale; the switch exists and starts off.
- **Limit 13 for the initial choice (the earlier proposal):** dropped; the timing manifest estimates about ten more hours at 16 threads for the persons with a 13-trip tour, against 634 s for the 9-11-trip file.
- **Renaming `frozen_pt_walk_lift`:** no, a rename would break its readers for no gain.

## Consequences

- With the defaults the initial mode choice reaches trips it skipped, so the modal split changes (by design); the size is measured by the replay and the 1 % comparison, not here. The effect over a full simulated day is for the next 100 % production run (#22).
- Import closure: `plan_check` now imports `mode_choice_reach`, so the closure of several stages widened and their cache tokens change: `analysis_suite`, `simwrapper_export`, `cut_schedule`, `supply_gtfs`, `incommuters`, `student_incommuters`, `outside_tour_modes`, `portal_trips`, `prepare`. A warm cache recomputes those stages once.
- Reading `plan_check.json` of an older run next to a new one: the `frozen` counts differ by the over-long tours (decision 8).
- The Java change must be merged and the jar rebuilt before the switch is used; the pipeline builds the jar from `eqasim_source_path` and both commits are recorded with the run.
- Limits not addressed: ordinary tours that keep a long walk although the mode choice reached them (the person has no other option) are only counted; routed pt trips with a long access or egress walk stay a report; the survey's round trips and the location choice (#375) are untouched; in-commuters and freight keep their own strategies (ADR-0182).
